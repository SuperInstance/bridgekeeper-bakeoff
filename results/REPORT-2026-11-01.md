# Bridgekeeper bake-off — report, 2026-11-01

Three implementations of one contract (SPEC.md) — **Elixir/BEAM**,
**Rust (std-only)**, **C++ (fork-per-request)** — plus a fourth
run: the **production Rust build** (`prod`) that si-ready's
wsl-npu-bridge adopted from the Rust contestant. All runs: same
black-box battery (battery/battery.py), same device (ProArt PX13,
WSL2), same live upstreams (Lemonade + FastFlowLM on the Ryzen AI
NPU, reached through the bridge's SSH reverse relay).

Scoring per SPEC: robustness events pass/fail with recovery
times; latency and footprint are numbers; no single weighted
score. Raw receipts: `results/*.json` in this repo (copied from
the device).

## The finding that mattered most

The single discriminating test was not speed — added latency is
noise for all three, exactly as the transport study predicted
(the NPU spends ~50 ms/token; no daemon can win or lose there).

It was **what a dead upstream looks like through the SSH relay**.
On direct loopback, a killed service is a clean
connection-refused and every implementation fails fast. Through
the relay, the socket can sit *open with nothing behind it* —
and then behavior diverges by design:

- Elixir's embed path carried a tight 1.5 s budget and returned
  502 in 1.5 s — the only clean pass of the contract's
  "502 within 2 s" line in this topology.
- The Rust contestant waited on a 30 s read timeout (designed for
  refusal semantics) and blew through the 2 s bound — measured
  >10 s, probe-guarded.
- C++ behaved like the contestant (curl read path >10 s), and
  showed two further chaos blemishes: its chat broke during the
  *Lemonade* outage (chat should not care — FLM was alive), and
  after the FLM restore its chat probes never returned a clean
  `done` inside the battery's 120 s recovery window, though the
  daemon itself stayed up and soaked perfectly afterwards.

The production Rust build closes this in two layers, both forced
by measurement. First attempt — handlers consult the health
poller's state and refuse known-down upstreams without dialing —
still failed the battery: a hand probe showed why. The poller
notices a kill at +2.0 s, but a request that dials *inside* that
blind window connects to the silent socket and hangs (measured:
no answer in 12 s). So the embed path gained a second layer:
a 1.8 s fuse on the response *headers*, after which the handler
re-checks the poller — down → 502 on the spot; still up → the
upstream is alive but cold (a first-ever embed on this stack
legitimately took 72.9 s), so the call is re-issued with the
generous timeout and waited out. "Down is answered instantly;
slow is waited out." Final battery result for that line:
**502 in 1.83 s**, and the production card is clean everywhere
else too (see the table).

## Harness failures (part of the record, per doctrine)

The battery itself failed twice before it measured anything, and
both failures were the harness's, not the contestants':

1. **Helper/module name collision.** The battery defined a helper
   named `http` in a module that also used `http.client`; every
   request raised AttributeError, swallowed by a blanket except,
   and all three daemons were reported "never became healthy"
   while verifiably listening. Fixed by renaming the helper;
   re-verified in isolation before any rerun.
2. **Unguarded probe call.** `phase_chaos_lemond` called the
   embed probe without a guard; two contestants out-waited the
   10 s probe (finding above) and the battery crashed with a
   traceback instead of recording the measurement. Fixed:
   `daemon_embed`/`direct_embed` never raise — a timeout returns
   status 0 with elapsed = the probe window, which *is* the
   measurement.

3. **Stale-file race (orchestrator error).** A source fix and the
   tar that deployed it were issued as parallel calls; the tar
   shipped the pre-fix bytes and the prod battery duly "failed"
   against code that was never on the device. The compiler error
   citing the old line number exposed it. Rule since: a deploy
   that depends on an edit is strictly serial, and the deployed
   file is read back on the target before anything is tested.

And one platform finding the battery surfaced about the *stack*,
not the daemons: after a hard kill, a bare restart of FastFlowLM
wedges in model load (no answer at 290 s). All restores in the
final runs go through the bridge's own `serve.ps1` — the
production recovery path — which is also the honest thing to
measure recovery against.

## Verdict

**Rust, for this job — adopted as the production bridgekeeper
in si-ready/wsl-npu-bridge.** Not because it won every line (it
didn't: Elixir took the dead-upstream embed line and the
in-run transcribe; C++ has the smallest binary and the hardest
handler isolation), but
because the daemon's job is *don't die and don't lie while
waiting on a slow NPU*, and Rust does that with the fewest
moving parts: zero dependencies, a 3 s offline build, 2.7 MB of
resident memory on a memory-tight laptop, no measurable added
latency, a perfect soak, and failure behavior that is mechanical
(socket timeouts + catch_unwind) rather than supervisory. Its
one measured contract violation was fixable in the production
pass without changing its architecture (above).

**When the alternatives are the right call** (argued in full in
si-ready's docs/WHY-RUST.md):

- **Elixir/BEAM** — when the front door grows into a many-client
  control plane: thousands of connections, hot upgrades,
  supervision as a platform. Its supervision tree rebuilds what
  dies by construction, /health reads can never block behind a
  sick poller, and its chaos record here was flawless. You pay
  ~150 MB idle and a runtime.
- **C++** — when handlers must parse hostile input or drive the
  NPU stack directly (ONNX Runtime GenAI / DirectML): fork-per-
  request gives containment threads cannot honestly promise, at
  the smallest binary size here. You pay hand-rolled HTTP and a
  listener that still needs an external supervisor.
